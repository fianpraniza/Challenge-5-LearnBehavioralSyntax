### New Understanding - `@State` vs Plain `var`
- `@State` is used when a SwiftUI `View` needs to store local data that can change and should cause the UI to update.
- A plain stored `var`, such as `var elapsedSeconds = 0`, is not the right source of truth for changing SwiftUI UI state.
- SwiftUI views are structs, and `body` can be recalculated many times.
- SwiftUI observes `@State` changes. When an `@State` value changes, SwiftUI can re-render the view.
- In this milestone, `elapsedSeconds` must be `@State` because the timer changes it repeatedly and `Text` must show the latest value.

Mental model:

```text
Timer tick
→ elapsedSeconds changes
→ @State notifies SwiftUI
→ body recalculates
→ Text displays updated time
```

### New Understanding - Why Not `@Published private(set)` Yet
- `@Published` is used when state lives inside an observable object, commonly a ViewModel or model object, not directly inside a SwiftUI View.
- `@Published` means: when this property changes, publish or announce the change to observers.
- `private(set)` means: other code can read the property, but only the owner object can change it.
- Original Tiempo uses `@Published private(set) var elapsedTime` because timer/session behavior lives in `PracticeViewModel`, not directly in the View.
- That pattern makes sense when logic includes multiple responsibilities such as recording, pause/resume, WPM, slide tracking, speech recognition, and session result handling.
- For Milestone 3 iOS learning, `@State` is simpler and better scoped because the timer behavior is local to `PracticeView`.

Short distinction:

```text
@State = local mutable state owned by a SwiftUI View.
@Published = mutable state owned by an ObservableObject and observed by a View.
private(set) = readable from outside, writable only from inside the owner type.
```

### New Understanding - Timer Publisher Flow
- `Timer.publish(every: 1, on: .main, in: .common)` creates a timer publisher that emits an event every 1 second.
- `.autoconnect()` makes the publisher start automatically when the view subscribes/listens to it.
- `.onReceive(timer)` listens for events emitted by the timer.
- The `_ in` means the closure receives the timer event value but does not use it.
- The timer event is better understood as a time event or tick, not as an automatic button tap.

Runtime flow:

```text
PracticeView appears
→ timer publisher starts emitting tick events
→ .onReceive(timer) receives each tick
→ elapsedSeconds += 1 runs
→ @State changes
→ SwiftUI recalculates body
→ formattedElapsedTime recalculates
→ Text updates on screen
```

### New Understanding - Computed Property for Timer Format
- `formattedElapsedTime` is a computed property, not `@State`, because it does not store independent data.
- It is derived from `elapsedSeconds`.
- `elapsedSeconds` is the source of truth.
- `formattedElapsedTime` is recalculated whenever the view body reads it after state changes.

Mental model:

```text
elapsedSeconds = raw stored timer value
formattedElapsedTime = display text derived from elapsedSeconds
```

### New Understanding - `/`, `%`, and `String(format:)`
- `elapsedSeconds / 60` uses integer division to calculate the minute part.
- Example: `125 / 60` gives `2`, because 125 seconds contains 2 full minutes.
- `elapsedSeconds % 60` uses modulo to calculate the remaining seconds.
- Example: `125 % 60` gives `5`, because 125 seconds equals 2 minutes and 5 seconds.
- `String(format: "%02d:%02d", minutes, seconds)` turns the two integer values into timer text.
- `%02d` means: format an integer with at least 2 digits, padding with `0` if needed.
- The first `%02d` is filled by `minutes`.
- The second `%02d` is filled by `seconds`.
- Example: `minutes = 2`, `seconds = 5` becomes `02:05`.
